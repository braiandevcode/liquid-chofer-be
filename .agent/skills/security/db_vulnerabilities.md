## DB_VULNERABILITIES

### RULES
- Verify, analyze, and fix with RIGOR:
- SQL injection (classic, blind time-based or boolean, error-based, UNION, and second-order): always use parameterized queries or prepared statements, never concatenate or interpolate user input into the query; validate with an allowlist the dynamic column and table names and `ORDER BY`, which cannot be parameterized.
- NoSQL injection (e.g. MongoDB): validate the type and schema of each field so that objects with operators (`$ne`, `$gt`, `$regex`, `$where`) do not arrive where a string is expected; avoid `$where` and server-side JavaScript execution; sanitize keys that start with `$` or contain `.`.
- Frameworks and ORMs (GraphQL, Prisma, MySQL, and others): use their safe APIs and review the points where protection is bypassed (e.g. `$queryRawUnsafe` and `$executeRawUnsafe` in Prisma, raw queries or `literal` in other ORMs, `multipleStatements` enabled in MySQL); in GraphQL, validate the arguments of each resolver, check authorization per field and object, limit depth, complexity, aliases, and batching, and disable introspection and field suggestions in production.
- Race conditions: make critical operations atomic (balances, coupons, stock, votes, single-use redemptions, invitations) with transactions, row locks (`SELECT ... FOR UPDATE`), optimistic locking with versions, `UNIQUE` constraints, and idempotency keys; do not rely on the "read, check, write" sequence in application code.
- Transactions: group related operations in a transaction with the appropriate isolation level; if the connection drops, a timeout occurs, an error happens, or a malicious pattern is detected, roll back, abort the flow, and do not continue with partial state (fail closed); define timeouts and controlled retries and always release connections.
- Secure and synchronized persistence: encrypt connections (TLS) and sensitive data at rest; store passwords with adaptive hashing (Argon2, bcrypt) and never in plain text; keep DB secrets and credentials out of the code; ensure consistency between database, cache, replicas, and queues (invalidate cache on write, avoid stale reads in security decisions); and keep versioned migrations and tested backups.
- Least privilege in the database: app user without administration permissions (`DROP`, `GRANT`, `FILE`), separate accounts by function (read and write), database not exposed to the Internet, and DB errors without internal details sent to the client.
- Detection of bots and malicious patterns: rate limits per IP, account, and endpoint, CAPTCHA or challenges on sensitive flows, detection of bursts and of injection or enumeration patterns, progressive temporary blocking, and logging with alerts for detected attempts.
- Allowlist and denylist: the allowlist is the primary control (allowed values, formats, fields, operators, and origins); the denylist only complements it (abusive IPs, patterns, or user agents) and must never be the only defense, because it is easy to evade.
- If a vulnerability is detected: fix it, test with payloads (`' OR 1=1--`, time-based injection with `SLEEP`, `UNION`, second-order, `{"$ne": null}` and `$where` in NoSQL, GraphQL with deep and batched queries, concurrent requests to trigger race conditions, and a connection cut in the middle of a transaction) to confirm it has been mitigated, and report to me the finding, its location, the cause, and the fix applied.
- Securely back up a backup copy
